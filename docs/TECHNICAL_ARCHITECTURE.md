# Technical architecture

## Stack
- **Godot 4.7.2-stable**, GDScript, **GL Compatibility** renderer (widest mobile GPU support,
  runs under Mesa/llvmpipe for CI screenshots). Portrait 720×1280 base, `canvas_items` stretch,
  `expand` aspect → layouts adapt to any phone/tablet ratio; safe areas applied via `UI.safe_margin`.
- No third-party addons or SDKs. Art is procedural; audio/icons are generated by `tools/`.

## Puzzle model
- **Directions** are bit flags `N=1 E=2 S=4 W=8`; `Dir.rotate_mask` rotates clockwise.
  This single model is used by the game, solver, validators and tests.
- **Tiles** declare `base_mask` and flags (`rotatable`, `accepts`, `transmits`, `emits`, `sink`,
  `gated`, `toggle`) in `TileTypes.DEFS`. Adding a mechanic = adding a definition (+ drawing).
- **Board** owns mutable state: tile rotations + `switches` (link → on). `tap()` is the only
  player move: rotates a rotatable tile 90° clockwise or toggles a lever. `snapshot()/restore()`
  power undo, reset and resume.
- **Gates** are open when `switch_on != inverted`.

## Water simulation (deterministic)
BFS from every source in fixed order. For each reached tile that transmits, every opening is
checked against the neighbour: out of bounds → `edge` leak; neighbour can't hold water →
`blocked`; closed gate → `closed_gate`; no facing opening → `mismatch`; otherwise connected.
Visited set prevents cycles; targets are sinks. The `WaterResult` lists distances (for
ring-by-ring fill animation), edges, reached targets/bonus, leaks with reasons, and
`all_required_reached`. The solve check never depends on animation.

## Solver
Uniform-cost search over **partial assignments**: flood with undecided rotatable tiles treated
as walls; branch on the first frontier tile's distinct orientations (cost = taps to reach the
cheapest equivalent rotation); switches decided up front (2^k). Reach is monotone in decided
tiles → first goal popped is optimal. Goals: required targets; + all bonus targets; sealed
network (no leaks). Bounded by an expansion budget → `unverified`, never a guess.
Used offline (`tools/validate_levels.gd`, CI) and at runtime for hints (40k budget; the
largest level needs ≈7k expansions).

## Save
`SaveStore` writes JSON to `user://luma_save.json` atomically (tmp → verify → current to
`.bak` → rename). Load order: main → backup → defaults; a corrupt file is preserved as
`.corrupt`. `normalize()` migrates by `save_version`, deep-merges defaults (never drops unknown
fields), and repairs invalid values (negative essence, duplicate collectibles, bad types).
Saved: completed levels (best moves, optional objectives met), essence, unlocked areas,
restoration stages, discoveries, hidden decorations, achievements, objective counts,
tutorial steps, in-progress board, settings, stats. Saved on solve, on settings change, on
area unlock, on back-navigation and on app pause/focus-out/close.

## Scene flow
`boot → (first launch) gameplay L1 → result → island (restoration plays) → next level …`
`menu ↔ island ↔ gameplay`, `menu ↔ collection`, `menu ↔ settings`. `Router.go()` fades and
passes params; `Router.dry_run` lets integration tests observe navigation.

## Rendering
`TileView` (Node2D per cell) draws with CanvasItem primitives; rotatable tiles turn their disc
(`rot_offset` tween). `BoardView` lays out cells to fit (≤175 px), converts touches to cells,
and schedules water fill by BFS distance. `IslandView` draws an isometric heightmap of areas
(painter's order), restoration objects as continuous growth values (animated by tweens),
decorations, mist over locked areas and spark bursts. `Painter` holds all shapes.

## Performance notes (measured)
Software GL (llvmpipe, Xvfb) runs gameplay at ~40 FPS and the island at ~16–20 FPS at
720×1280; real mobile GPUs are expected to be much faster but **no device measurement exists
yet** (see QA_STRATEGY). Exported pack (`.pck`) is ~1.3 MB; debug APK 59 MB (two ABIs,
debug engine).
